งานวิจัยด้าน usability ที่ศึกษาว่าประสบการณ์การช็อปปิ้งบน Amazon ติดขัดตรงไหน สำหรับผู้ใช้ตาบอดที่ต้องใช้ screen reader

## Empathize

เราหาผู้เข้าร่วมเป็นผู้หญิงตาบอดสามคน อายุ 53 ถึง 76 ปี ผ่าน Professor Oliver Alonzo อาจารย์ที่ปรึกษาของเรา ทั้งสามคนใช้ JAWS ทุกวัน (สองคนใช้บนคอมพิวเตอร์ตั้งโต๊ะ อีกคนใช้บนแล็ปท็อป) แต่ความชำนาญในการใช้ต่างกันมาก ซึ่งกลายเป็นเรื่องที่สำคัญที่สุดในการศึกษานี้

ผมช่วยออกแบบ task scenario ทั้งสามแบบ ได้แก่ ค้นหาและกรองสินค้า เพิ่มลงตะกร้า และชำระเงิน ซึ่งเป็น flow การช็อปปิ้งจริงที่ผู้ใช้ตาบอดจะทำ ไม่ใช่ task ที่สร้างขึ้นในห้องแล็บ ก่อนแต่ละ task เราให้ผู้เข้าร่วมให้คะแนนว่าคาดว่าจะยากแค่ไหน และหลังแต่ละ task ผู้เข้าร่วมทำแบบสอบถาม ASQ (After-Scenario Questionnaire; ใช้สเกล ASQ มาตรฐาน: 1 = ง่ายที่สุด, 7 = ยากที่สุด) และให้สัมภาษณ์แบบ semi-structured แต่ละ session ใช้เวลา 45 ถึง 60 นาที โดยเราอ่านเอกสารขอความยินยอมให้ฟังตั้งแต่ต้น เพื่อให้ผู้เข้าร่วมยืนยันได้ว่าเข้าใจก่อนเริ่ม

ผมเป็นผู้ดำเนิน session หนึ่งในสามครั้งด้วยตัวเอง ทั้งพาผู้เข้าร่วมทำ task ดูแลการบันทึก และจดโน้ตแบบ real-time และยังเข้าสังเกตการณ์อีกหนึ่ง session เพื่อเก็บสิ่งที่ผู้ดำเนินอาจพลาดไป

## Define

E-commerce ทำให้การช็อปปิ้งสะดวกกว่าที่เคย ยกเว้นถ้าคุณตาบอด Screen reader อ่านเนื้อหาบนหน้าเว็บทีละบรรทัด ทั้งโฆษณา แบนเนอร์ ป๊อปอัป และข้อมูลที่อัปเดตแบบ dynamic ทั้งหมด สิ่งที่ผู้ใช้ที่มองเห็นรู้สึกว่าเป็นประสบการณ์ช็อปปิ้งที่ครบครัน กลับเต็มไปด้วยเสียงรบกวนสำหรับคนที่ใช้เทคโนโลยีสิ่งอำนวยความสะดวก (assistive technology) Amazon ซึ่งเป็นแพลตฟอร์ม e-commerce ที่ใหญ่ที่สุดในสหรัฐฯ ยังไม่ผ่านแนวทาง WCAG ในส่วนของเนื้อหาที่ทำให้ประสบการณ์ดู "ทันสมัย" นั่นเอง ได้แก่ dropdown menu, carousel, ป๊อปอัป และการอัปเดตแบบ real-time

![แผนภาพ task การช็อปปิ้ง ตั้งแต่ค้นหาและกรอง เพิ่มลงตะกร้า ไปจนถึงชำระเงิน โดยมีโฆษณาและแบนเนอร์ carousel ป๊อปอัป และการอัปเดตแบบ live แย่งความสนใจอยู่ทุกขั้นตอน](/images/amazon-accessibility/define-shopping-and-distractions.webp "เนื้อหาแบบ dynamic แย่งความสนใจตลอดเส้นทางการช็อปปิ้ง")

เราตั้งคำถามหลักของการศึกษาไว้สามข้อ ผู้ใช้ที่ตาบอดและสายตาเลือนรางเจออุปสรรคอะไรบ้างกับเนื้อหาแบบ dynamic แบบนี้? อุปสรรคเหล่านั้นส่งผลต่อการนำทางและการทำ task ให้สำเร็จจริง ๆ อย่างไร ไม่ใช่แค่ในทางทฤษฎี? และการเปลี่ยนแปลงด้านดีไซน์แบบไหนจะช่วยปิดช่องว่างนี้ได้? งานวิจัยก่อนหน้า (Lazar et al., 2007) ได้รวบรวมไว้แล้วว่าอะไรทำให้ผู้ใช้ screen reader หงุดหงิดบนเว็บโดยทั่วไป เราอยากเห็นว่าความหงุดหงิดเหล่านั้นเกิดขึ้นอย่างไรบนแพลตฟอร์มเดียวที่มีผลกระทบสูง

## Test

ผมทำการวิเคราะห์ ASQ และสร้าง affinity diagram เพื่อสังเคราะห์ผลจากทั้งสาม session จากนั้นนำเสนอรายงานวิจัยฉบับสุดท้ายต่ออาจารย์ที่ปรึกษา ผลที่ได้คืออุปสรรคที่เกิดซ้ำ ๆ ห้าข้อ:

**ข้อมูลมากเกินไป (information overload)** ผู้เข้าร่วมทุกคนรู้สึกเหนื่อยกับเนื้อหา "ส่วนเกิน" จำนวนมากที่ต้องนั่งฟังผ่านไป P3 พูดไว้ตรง ๆ ว่า *"The constant pop-ups make it hard for me to stay focused on what I am doing."* (ป๊อปอัปที่เด้งขึ้นมาตลอดทำให้จดจ่อกับสิ่งที่กำลังทำได้ยาก)

**การกรองที่ใช้ไม่ได้ (broken filtering)** แถบเลื่อนช่วงราคา (price range slider) ใช้ร่วมกับวิธีนำทางบางแบบไม่ได้ P2 กรองตามราคาไม่ได้เลย จึงต้องไล่ดูผลการค้นหาเองแทน ซึ่งก็มักได้สินค้าที่ไม่เกี่ยวข้องอยู่ดี

**สับสนเรื่องตะกร้า (cart confusion)** P1 และ P2 ต้องกลับไปเช็กตะกร้าอีกครั้งตอนชำระเงิน เพราะป๊อปอัปขัดจังหวะ flow การเพิ่มลงตะกร้า จนไม่แน่ใจว่าเพิ่มอะไรเข้าไปแล้วบ้าง

**ความช่วยเหลือที่ไม่สม่ำเสมอ (inconsistent support)** ผู้เข้าร่วมสองคนโทรหาสายช่วยเหลือด้าน accessibility ของ Amazon เป็นประจำ แต่ได้ผลไม่แน่นอน คนหนึ่งเล่าว่า Amazon Access ซึ่งเป็นฟีเจอร์ด้าน accessibility โดยเฉพาะ ถูกยกเลิกไปแล้ว *"There used to be Amazon Access, and it was great, but now it's gone."* (เคยมี Amazon Access และมันดีมาก แต่ตอนนี้ไม่มีแล้ว)

**ช่องว่างด้านทักษะที่ไม่เท่ากัน (unequal skill gap)** นี่คือสิ่งที่เปลี่ยนมุมมองของผมต่อทั้งโปรเจกต์ ผู้เข้าร่วมคนหนึ่งผ่านขั้นการกรองไปไม่ได้ ส่วนในอีก session หนึ่ง ผู้เข้าร่วมอีกคนใช้งานทั้งเว็บไซต์ (รายการสินค้า ตัวกรอง และการชำระเงิน) ด้วยคีย์ลัดอย่างเดียว ด้วยความเร็วที่ดูธรรมดามาก เว็บไซต์เป็นแบบเดียวกันทั้งสองครั้ง ตัวแปรเดียวคือความชำนาญในการใช้เครื่องมือ ช่องว่างนี้ใหญ่มาก และดีไซเนอร์แทบมองไม่เห็นเลย เพราะการทดสอบ accessibility ส่วนใหญ่ไม่ได้คำนึงถึงเรื่องนี้ เราออกแบบให้ "ผู้ใช้ตาบอด" เหมือนเป็นกลุ่มเดียว แต่พวกเขาไม่ใช่กลุ่มเดียว

ข้อเสนอแนะของเรามาจากสิ่งที่เห็นโดยตรง ไม่ใช่จาก checklist ด้าน accessibility ทั่วไป:

1. โครงสร้าง heading ที่ชัดเจนและ skip link เพื่อลดภาระทางความคิด (cognitive load) จากเนื้อหาส่วนเกิน
2. ให้ผู้ใช้หยุดหรือปิดป๊อปอัปและการอัปเดตแบบ live ได้ และใช้ ARIA live region เฉพาะจุดที่มีประโยชน์จริง ๆ
3. ตัวกรองที่ใช้คีย์บอร์ดได้ทั้งหมด พร้อม feedback แบบ real-time เมื่อเลือก
4. ความช่วยเหลือด้าน accessibility ที่เชื่อถือได้ จากเจ้าหน้าที่ที่ผ่านการฝึกอบรม แทนประสบการณ์ call center ที่ไม่แน่นอน
5. Onboarding การใช้ screen reader ในแอป เพื่อไม่ให้ความชำนาญในการใช้เครื่องมือกลายเป็นเงื่อนไขของการใช้เว็บไซต์

## Reflect

ผู้เข้าร่วมสามคนถือเป็นกลุ่มตัวอย่างที่เล็ก และทั้งสามคนตาบอดสนิท เราไม่ได้ศึกษาผู้ใช้ที่มีสายตาเลือนราง ซึ่งเจอความท้าทายอีกแบบ และช่วงอายุของเรา (ทั้งหมดอายุ 50 ปีขึ้นไป) น่าจะทำให้ผลเอนไปทางผู้ใช้ที่ไม่คุ้นกับเทคโนโลยีสิ่งอำนวยความสะดวกรุ่นใหม่ ๆ

แต่สิ่งที่ติดอยู่ในใจผมมากที่สุดไม่ใช่ข้อจำกัด มันคือการตระหนักว่า accessibility ไม่ได้มีแค่ผ่านหรือไม่ผ่าน เว็บไซต์หนึ่งอาจผ่าน WCAG ในทางเทคนิค แต่ยังใช้งานไม่ได้จริงสำหรับผู้ใช้จำนวนมาก เพราะการผ่านมาตรฐานวัดที่ตัว interface ไม่ได้วัดที่คนที่ใช้งาน ทักษะที่ผู้ใช้มีต่อเทคโนโลยีสิ่งอำนวยความสะดวกของตัวเองส่งผลต่อประสบการณ์พอ ๆ กับดีไซน์ นี่ไม่ใช่ข้ออ้างให้ดีไซน์แย่ได้ ตรงกันข้าม มันยิ่งทำให้มาตรฐานสูงขึ้น การออกแบบที่เข้าถึงได้ต้องใช้ได้ทั้งกับมือใหม่และผู้เชี่ยวชาญ ไม่ใช่ให้รางวัลแค่คนที่ฝึกมามากที่สุด
